# MerMarkd 开发流程与工程规则（v1）

> 2026-09-17。适用于从技术原型到可下载安装的 Windows 首版。当前按单人开发估算，优先做可运行的纵向切片；本文件规定实施方式，不替代[产品与架构方案](PRODUCT_ARCHITECTURE.md)。

## 1. 目标与约束

交付目标是用户能安装、打开本地 Markdown、在编辑/阅读/卡片三模式工作、保存、导出完整画布的 Windows 软件。项目分阶段完成，每个阶段结束时必须保持可启动、可回退。首版只处理单个本地 `.md`；遇到不支持的输入，要明确提示，不能改坏原文件或静默丢掉画布关系。

开发决策以用户最新要求为准；产品语义见 `PRODUCT_ARCHITECTURE.md`，具体技术变化记录在 `docs/DECISIONS.md`。对未明确的普通实现细节直接做可逆决定并记录，不把常规开发工作停在反复确认上。凡改变 Markdown 文件规则、首发平台或导出承诺的决定，先形成可审查的原型与影响说明。

## 2. 工作顺序与阶段门槛

| 阶段 | 先完成什么 | 进入下一阶段的证据 |
| --- | --- | --- |
| P0 可行性 | 建仓与可启动桌面壳；打出一次测试安装包；验证章节抽取与最小文本补丁；验证嵌套卡片和 PDF/JPG 整图导出 | 记录样本文档、运行命令、测试结果、限制和选型决定；关键路径没有未解释的数据损坏或裁切 |
| P1 文档基础 | 打开/保存、编辑模式、阅读模式、目录与定位 | UTF-8/BOM/CRLF 读写往返；外部改动冲突不覆盖；渲染安全基线通过 |
| P2 卡片基础 | 标题树、初始布局、拖动位置、展开/收起、伴随数据 | 关闭重开能恢复画布；拖动、折叠、缩放不改 `.md` 摘要 |
| P3 结构与关系 | 用户箭头、结构拖入预览、标题级别调整、撤销、ID 修复 | 边界样本全部通过；一次操作可完整撤销；不确定的连线不错误重接 |
| P4 导出与质量 | PDF/JPG/PNG、分页/分块、性能、键盘操作 | 视口外内容不裁切；中文字体、本地图片、长卡片和跨页箭头有确定行为 |
| P5 发布 | Windows 安装包、签名条件检查、安装/卸载、版本与发布说明 | 在没有开发工具的干净 Windows 环境完成安装、打开、保存、导出和卸载 |

阶段不是一次性大开发。每阶段拆成可运行的纵向切片：例如“打开文件→解析标题→显示卡片→保存布局”，先跑通，再扩展细节。第一个测试安装包在 P0 生成，避免到最后才发现打包问题。原型验证失败时，先缩小输入或替换局部实现；只有数据模型或核心需求不可达时才整体换栈。

## 3. 每个切片的固定流程

1. **先写验收例子。** 给出用户操作、预期文件变化、预期画面或导出结果；结构编辑必须包含操作前后 Markdown 样本。
2. **确定边界。** 标记它改的是 `.md`、伴随 JSON、应用本地状态还是导出文件。卡片可视状态不能直接成为 Markdown 的内容来源。
3. **实现最小闭环。** `src/core` 纯逻辑先于界面事件；主进程文件能力通过类型化的最小 IPC 提供；界面只调用明确命令。
4. **验证风险。** 有数据损坏可能的变换写单元与往返样本；交互用集成测试；导出用真实渲染和视觉检查；安装包做干净环境冒烟测试。纯样式等低风险改动不机械增加测试。
5. **更新状态。** 在 `docs/PROGRESS.md` 记录完成、验证命令、未解决问题和下一切片。重大选型变化写 `docs/DECISIONS.md`，说明替代方案和后果。
6. **保持可运行。** 提交前至少完成类型检查、相关测试和打包构建；无法运行的中间实现必须明确标记，不当作已完成阶段。

## 4. 不可破坏的工程不变量

| 不变量 | 如何验证 |
| --- | --- |
| 普通卡片拖动、缩放、折叠、连线、导出不改 `.md` | 操作前后对原文件计算摘要；用实际磁盘文件验证 |
| 结构拖入只移动完整章节子树并调整适用标题；不重排其他正文 | 对原文字段做局部补丁；移动后重新解析并比较非目标块；不安全时拒绝操作 |
| 所有源文件写入可恢复 | 写前核对磁盘版本；临时文件写入并替换；结构保存前有恢复快照 |
| 同一操作可撤销 | 文本与画布状态作为一个命令事务进撤销栈 |
| 卡片与箭头不误连到重名章节 | 稳定 ID 与保守匹配；歧义时进入待修复状态 |
| 保存后源文档和伴随文件版本一致 | 伴随文件记源摘要；未保存的结构草稿放恢复日志，不能先写成“已提交”侧边状态 |
| 导出不静默裁切 | 根据完整图边界计算页/块；超限报出尺寸，分页或多图输出；测试视口外卡片 |

## 5. 代码与安全边界

- TypeScript 使用严格类型；文档解析、章节树、结构变换、ID 对齐属于无 UI 依赖的 `src/core`。React Flow、Electron 对象不进入核心领域类型。
- 文件 I/O、打印和图片编码留在 Electron 主进程；渲染进程启用隔离与 sandbox，禁用 Node 集成。preload 只暴露经过路径和参数校验的打开、保存、导出接口。
- Markdown 阅读和卡片正文使用同一受控渲染管线；不执行原始 HTML 或脚本。网络资源和外链打开必须经过明确的协议与路径策略。
- 所有文件写入保留原编码/BOM/换行策略。首版对不支持编码只读并提示转换；不能猜测编码后覆盖。
- UI 状态、内容状态、磁盘状态分别管理。用户能看出“Markdown 未保存”“画布布局未保存”和“导出中”状态。
- 依赖固定版本并提交锁文件。引入原生模块前先跑安装包验证，避免开发环境可用而发布包缺模块。
- 不把绝对用户路径、Markdown 正文或私有导出内容写入遥测。错误日志只保留必要诊断信息；默认离线运行。

## 6. 验证样本与质量门槛

P0 起建立小型文档样本集，至少覆盖：空文件、无标题、前言、同名标题、跳级标题、六级标题、Setext、CRLF、BOM、代码围栏中的 `#`、引用/列表中的标题、GFM 表格、中文、相对图片、长章节、外部文件改动。结构操作增加“移动到自身/后代/当前父卡”“跨越六级”“移动后相邻块解析变化”样本。

测试分层：`core` 样本测试保证语义和文件字节；UI 测试覆盖投放区、确认/取消、展开/收起、连线和模式定位；导出测试检查整图边界、页数、可读性和文件打开；桌面冒烟测试检查安装、启动、打开、保存、导出与卸载。性能预算先作为目标而非承诺，用 P0 实测确定上限。

## 7. 版本与发布规则

采用 Git 与小步提交；发布版本从测试安装包开始标注版本号。P0 安装包可以未签名，仅供本机验证。公开分发前再完成签名、许可证清单、发布说明和干净机器测试；签名证书与发布渠道属于发布阶段的外部依赖，不阻碍前期实现与本地安装包验证。

阶段完成的定义是**能从干净检出按文档构建并通过对应验收**，而不是代码已写完。若验证门槛未过，`docs/PROGRESS.md` 如实记录限制和下一步修复，不提前宣称完成。
