# PERF3C：源码输入热路径

> 2026-10-16；基于已合并 PERF3B / PR #10（b0c6cd9）。本批输入切片已完成，整体性能及 P0 未完成。

## 验收例子

1. 原生输入、连续输入、替换、撤销与重做仍共用一个 LF 编辑会话；BOM、CRLF、emoji 与尾换行按原合同保存。
2. 界面层不为已使用共享历史的输入再次扫描全文；相同源码的 IPC 确认和草稿确认复用 LF 缓冲区，不重建撤销历史。
3. 输入立即进入 dirty，主进程仍逐 revision 接受完整源码；保存等待队列，过期确认不能覆盖较新的输入。拒绝更新后恢复主进程确认版本。
4. 未保存输入、撤销和模式切换保持 Markdown/YAML/JSON 字节及 mtime 不变；dirty 期间批注和结构写入继续冻结。
5. 同机 1/5 MiB 各五次，分开报告输入事件、处理、后续帧以及含自动化等待的命令时间；保留退化结果。

## 设计复核

| Before | After | Why |
| --- | --- | --- |
| 界面和共享历史各扫描一次全文差异 | 共享历史负责单次差异扫描；独立编辑器保留本地历史 | 减少每次键入的同步工作 |
| 反复转换当前源码和候选源码的 LF/CRLF | 复用共享 LF 会话，候选只在 IPC 前转换为原换行 | 降低分配成本，保留逐版本同步 |
| 同内容确认也重新派生 LF 文本 | 确认复用当前会话及历史 | 避免无内容变化时重复复制 |

## 输入与确认边界

`useMarkdownEditor` 在打开、恢复、放弃、保存、主进程拒绝及结构变更时同步发布源码 view 和对应的 LF 会话；普通键入复用这份会话。仅相同源码的确认跳过再次 LF 投影，内容不同的确认仍核对/重建会话。原有 epoch、generation、mutation token、逐 revision 队列和保存等待均保留，没有合并或延迟主进程 dirty 同步。

源码视图在有共享会话时不创建永远不会使用的本地差异记录；没有共享会话时继续使用原本地历史。外壳直接读取共享 LF 缓冲区，只有会话尚未建立时才从源码派生。没有更换 textarea、渲染 Markdown、虚拟化、增加依赖或修改持久化格式。

## 性能口径与结果

同一 Windows 主机、1200×800、focus emulation；旧版来自 PERF3B 安装包，当前版为生产 package。固定的 BOM/CRLF/中文/emoji 语料：1,058,744 字节 / 205 标题和 5,288,903 字节 / 1024 标题。每档交替运行旧版和新版五对独立进程，无并行构建或窗口回归。末尾撤销输入并检查三文件 bytes/mtime。最终样本 `out/qa/perf3c-paired-{before,after}-{1m,5m}-{1..5}.json`，汇总 `perf3c-measurements.json`。

- 原生输入段：textarea `beforeinput` 捕获到 `input` 捕获。
- 输入处理段：`input` 捕获到 window 冒泡监听；覆盖根节点的 React 处理及同步提交，不等同于纯业务函数耗时。
- 事件至后续帧：`beforeinput` 到两次 rAF 回调；是帧机会测量，不证明像素实际显示或所有异步任务完成。
- 命令时间：CDP 插入文本、dirty 条件轮询及后续两帧，含自动化和调度等待。最长帧间隔为该操作期间的最大 rAF 间隔。
- Script/Layout 是该命令区间 `Performance.getMetrics` 差值；renderer used heap 未强制 GC，不含 main/Worker/RSS。

## 剩余调度与布局

Worker 内新增数字时间戳 `analysisStartedAt`（performance.timeOrigin + now），与界面的同源时间基准区分“发送请求 → 开始分析”和“分析结束 → 收到回复”；不改变任务取消或返回的数据语义，不写产品遥测。旧包没有该字段，不能反推其两个分段。

当前版最终样本中，1 MiB 发送至开始分析中位数/最差 **373 / 391.1 ms**，5 MiB **1888.5 / 1911.4 ms**；分析结束至回复分别为 **6.7 / 9.5 ms** 和 **33.8 / 35.7 ms**。这个首段包含 Worker 启动、模块载入、消息投递与调度，不能全部归为计算或 structured clone。前期诊断中也出现 5 MiB 首段约 25.5 ms 的样本，证明存在明显运行状态波动，尚未定位平台原因。

5 MiB 收到回复至后续帧仍约 430 ms，正文布局/绘制尚未优化。下一批 PERF3D 优先确认启动调度、正文布局和 200 可见卡片/大量批注的实际窗口预算，然后继续 UX6B → UX7 → UX8 → QA1。完整 Markdown 语义、选区、锚点与全场景导出是优化约束；P0 及整体性能门槛未完成。

## 诊断失败与限制

- 最初用捕获监听中的 microtask 标记处理结束，浏览器在后续监听前执行它，读数为 0；改用 window 冒泡监听，废弃该诊断读数。最终前后样本都使用相同监听口径。
- 初期分段运行新旧版本时首屏等待和 CPU 耗时波动明显，改为新旧交替五对采样。`before/after` 和带 profiler 的记录仅用于诊断，最终表格只使用 `paired-*`。
- CPU profile 最初误用 require 读取 `.cpuprofile` 导致语法错误，改为 JSON.parse；ASAR 定位改用 Windows path.join。成功定位到界面 changedSpan 和共享 changedRange 的两个全文扫描，未把压缩函数名直接当作来源证据。
- Node 的既有 MODULE_TYPELESS_PACKAGE_JSON 提示不阻止检查，本批未调整模块类型。真实中文 IME、物理多屏 DPI、干净机器安装/升级/卸载尚未验证。
