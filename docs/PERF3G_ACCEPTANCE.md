# PERF3G：可取消的后台画布准备

> 2026-10-20；基于已合并 PERF3F / PR #14（a6a5a5d）。当前切片已实现并通过功能和规模验证，仍属于原设计路线第 3 批 PERF3，整体退出条件未满足。

## 范围与边界

PERF3F 的 5 MiB / 200 卡片切换中位数 2249 ms，最长帧间隔 1154 ms。首次章节解析、锚点匹配和卡片文本仍在界面线程。本批优先处理这条首次准备路径；主进程保存核验、保存期间只读和落盘流程保持，保存响应继续测量。

| Before | After | Why |
| --- | --- | --- |
| CanvasEditor 渲染时解析全文，加载后在界面线程匹配与解析每节正文 | 同一后台任务创建精确源码快照、核验匹配并准备卡片文本 | 避免解析长任务阻塞模式切换 |
| 异步加载只靠 generation 忽略结果，同步解析不能中断 | 每次准备独立 Worker；离开、重载或源码变化终止旧任务并结算等待者，generation 拒绝已排队回复 | 取消能停止计算，旧文档或 dirty 结果不能回填 |
| v2 核心模块间接静态载入 ELK | 布局调用才动态导入既有 ELK 模块 | 准备 Worker 不再携带布局引擎；脚本 1,605,635 → 157,431 字节 |

Worker 只消费克隆后的源码、BOM 与已有画布模型，返回章节树、匹配结果和文本；不返回 parser AST、不访问磁盘、不拥有保存权限。结构、锚点与正文语义沿用既有 core 函数。页面只接受当前 path/source/BOM/dirty/reload 对应的任务，按结果建立只读文本缓存；缺项报错，没有回退到界面线程同步解析。完成、取消或错误都会终止 Worker，超时 30 秒，沿用现有自然语言错误与重新载入入口。

几何构建、节点提交、尺寸测量、初始及用户请求的布局仍在原路径。ELK 调用本来即为异步，只改变模块载入时机；布局算法、位置启发式及完整导出合同不变。源码结构变换、批注、三文件摘要/冲突/恢复与 dirty 冻结不改。没有新增依赖、preload IPC 或持久化格式；package.json 只新增窗口验收命令。

代价：每次进入卡片重新创建 Worker，存在模块加载、结构化克隆及临时内存成本；没有跨模式缓存、持久后台服务或全局文档历史。单线程 renderer 堆不能代表 Worker 和全应用 RSS。

## 验证设计

- core 对照原流程与 structuredClone 后的准备结果：空文件、前言、重复/歧义、Setext、围栏/引用、表格/HTML、BOM/CRLF、emoji/组合字符、呈现字段及完整场景；缓存只读和缺项拒绝。
- 任务单测覆盖替换/取消、旧与错误 ID 回复、创建/发送/运行/解码/响应失败及超时，等待者会结算，没有同步回退。
- 新 PERF3G 打包窗口专项拦截真实 Worker 回复，验证 pending 零卡片与写入禁用、实际任务回复前取消、dirty 源码撤销、跨文档旧回复、失败/重试、所有 Worker 释放、三文件 bytes/mtime 与缺失 sidecar 零创建。沿用 200 卡片/500 高亮、实际指针拖动、撤销重做与正文缓存生命周期检查。
- 沿用上批 1/5 MiB、200 标题、500 高亮、预存 20×10 网格的五对交替普通采样；旧版为上批最终 package 的独立副本。计时含自动化等待与后续帧，三次拖动分别等待保存，不称为持续拖动。普通样本不启用 CPU profile/强制 GC，且不并行构建或窗口回归；诊断分开。

## 验证过程

类型检查与 302/302 单测通过。最终 package、新窗口专项、既有 24 套窗口回归及真实 Vite 专项通过，共 25 套窗口验收。1 MiB 实际未回复任务的模式切换取消样本约 3 ms（单个诊断样本，不作为五次性能结论）。UX2 首轮“专注模式后撤销”超时，原脚本复跑通过；未确定原因，原失败日志保留，不声称稳定性问题已修复。

初始测试使用重复的 ID 生成器，触发既有唯一 ID 拒绝；改为独立新 ID 序列后通过，没有放宽产品规则。第一轮普通采样发现 Worker 静态携带 ELK，停止采样并改为按布局调用加载；`paired-*` 为调整前探索记录，不纳入最终结论，最终样本使用 `final-paired-*`。

## 结论、退化与独立诊断

主要收益是准备期间的响应：5 MiB 卡片切换最长帧间隔中位数 **1154 → 134 ms**（最差 1183 → 146 ms），1 MiB 为 375 → 129 ms。5 MiB 完全就绪时间仅 **2265 → 2209 ms**，计算没有凭空消失；Worker 的模块加载、解析、锚点匹配、文本准备和克隆仍耗时。准备期间界面能响应模式切换，并不等于卡片完成时间达到 300 ms。

保存路径未改，5 MiB 首次拖动至确认 **1729 → 1736 ms**，后两轮 1615 → 1610 / 1634 → 1612 ms，属于接近持平，不能计为本批保存优化收益。1 MiB 三轮保存中位数反而 891 → 918 / 769 → 804 / 757 → 797 ms。

其余退化如实保留：5 MiB 打开阅读中位数 **1658 → 1835 ms**，适应全图 **24 → 92 ms**；1 MiB 打开阅读 830 → 859 ms，适应最差 119 → 175 ms。1 MiB 第二次拖动后未强制 GC 的 renderer 堆中位数 **36 → 66 MiB**，返回阅读 **18 → 46 MiB**；5 MiB 多数 renderer 堆采样下降。模块加载/GC/调度分布发生变化，五对样本不足以确定各退化的因果，也不能把 renderer 堆下降称为全应用内存下降。

独立 5 MiB CPU/GC 诊断与普通样本分开。页面首次卡片 profile 总时长 2535 → 2257 ms；新版约 1914 ms 为页面线程 idle，剩余提交/布局等仍在页面，Worker 计算不在此 profile 内，不能说总 CPU 工作减少了同样比例。首次拖动 main profile 1765 → 1776 ms，Markdown parse 包含时间 946 → 921 ms，保存准备约一秒的解析仍未解决；包含时间有重叠，不能相加。
