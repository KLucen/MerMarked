# PERF3F：画布源码投影与事务核验复用

> 2026-10-19；基于已合并 PERF3E / PR #13（4d56ea4）。当前切片实现与验证完成，仍属原设计路线第 3 批 PERF3，整体性能退出条件未满足。

## 范围与边界

上一批 5 MiB / 200 卡片切换中位数 3381 ms，拖动至保存确认 4837 ms。CPU 诊断显示保存约 3849 ms 在章节解析调用链。本批去掉同一次画布加载/保存里的重复章节和锚点准备，不修改用户流程、布局、保存时只读保护或持久化格式。

| Before | After | Why |
| --- | --- | --- |
| CanvasEditor 解析章节后，reconcile 再解析一次相同源码 | 界面几何与匹配共用精确源码快照的冻结章节树 | 消除首次切换的重复全文解析 |
| 事务 prepare/load 各先解析章节，再为画布匹配重新解析和生成锚点 | 一次保存内共享章节树和源锚点描述；独立 prepare/commit/recover 仍可各自工作 | 降低拖动后的保存等待，保留所有文件和候选核验 |
| 缓存容易被同 hash 的错误字节或外部对象变化误用 | 每次调用复制并核对 UTF-8 字节、源码与 SHA；只接受核心创建的快照 | 缓存不能成为绕过数据校验的入口 |

`CanvasSourceSnapshot` 由 core 创建并深度冻结章节树，只包含精确 source 与紧凑树；不保存 parser AST。内部 WeakMap 只按快照对象持有一份锚点描述 Promise，BOM/摘要变化替换它，不持有跨文档历史。复制输入字节发生在异步 digest 之前；命中缓存仍验证摘要与严格 UTF-8，并拒绝非工厂快照或不同源码。每个候选画布仍重新做 schema、唯一匹配和歧义核验，不缓存“候选已通过”的结论。

新 `prepareAndCommitDocumentTransaction` 将上下文限制在一次保存。publish 仍读取 journal、重新读取并核验三个 before/after 快照，核验候选、获取锁并在发布各文件前后重查磁盘。没有把快照对象写进 journal、preload 或 sidecar；中断恢复、独立提交、清单检查使用新上下文。正文结构变换保持原独立重解析路径，批注范围核验保持原路径。

## 验证设计

- 对照有/无缓存的 v1/v2 匹配，覆盖空文档、虚拟卡片、同名标题、重复候选、Setext、围栏、引用块、前言、BOM/CRLF、emoji/组合字符；候选位置/正文显示保持。
- 预热后篡改字节、错误源码、非法 UTF-8、伪造快照仍拒绝；冻结章节树不可修改，外部修改返回锚点不能污染下次结果，异步进行时修改调用方字节不能改变已捕获来源。
- 真实磁盘验证两代画布的保存、Markdown/YAML bytes/mtime、完成凭据、发布中断后独立恢复、外部重建冲突和当前基线伪造锚点零写入。
- 沿用 PERF3E 的 200 卡片/500 高亮窗口样本，包括全部可见、查找、三次真实拖动与撤销重做、同标题正文编辑/撤销、dirty 冻结和文件边界。测试开始时显式显示并激活自身窗口，避免 Windows 隐藏/遮挡造成帧等待；此动作在计时起点前，对旧/新版一致。

## 测量口径

旧版为 PERF3E 安装包 nupkg 解出的 EXE，新版为本批 package。同机 1200×800 CSS px，1/5 MiB 各交替五对；每次重启、独立临时文件、不并行构建/窗口测试、不启用 profile/强制 GC。沿用预存 20×10 网格，未修复自动平排。

命令耗时包含自动化、条件等待与后续帧。拖动含六步指针移动及保存确认，三轮之间等待保存，不代表不中断连续拖动。renderer 堆采样不是全应用内存，未强制 GC；诊断样本与普通计时分开。

## 退化、内存与剩余成本

5 MiB 卡片切换中位数 3180 → 2249 ms，最长帧间隔 2079 → 1154 ms；首次拖动至保存确认 4551 → 1735 ms。拖动的最长帧间隔中位数保持 67 ms，本批主要减少保存等待，并未消除首次准备长任务。

退化保留：5 MiB 打开阅读 1655 → 2570 ms，卡片后 renderer 堆中位数 65 → 112 MiB，返回阅读后 55 → 137 MiB；1 MiB 打开阅读 843 → 898 ms、首次拖动堆 44 → 50 MiB，5 MiB 查找 86 → 96 ms。阅读运行路径没有修改，但两版 Worker 请求至开始分析均有双峰：旧版 31/1065/1062/118/74 ms，新版 1053/1077/74/1026/72 ms；批注加载均约 1.0–1.1 秒。现象与既有启动调度竞争相符，尚不足以确定因果或排除回归，不宣称所有路径改善。

独立 5 MiB GC 诊断在三次拖动撤销回原网格后进行画布/阅读三轮切换。旧/新版六个阶段 renderer 堆分别均为：卡片 47.6、阅读 31.4、卡片 45.1、阅读 31.5、卡片 45.2、阅读 31.6 MiB（各值四舍五入到 0.1 MiB）。这只说明有限轮次的强制回收后保留量接近；日常未强制 GC 的采样升高仍是实际观察，不能据此宣称内存退化消失或没有泄漏，也未测全应用 RSS。

CPU 诊断单独进行，不计入上面的五对普通样本。首次卡片 profile 总时长约 3283 → 2433 ms，Markdown parse 包含时间约 2639 → 1792 ms；首次拖动 main profile 约 4579 → 1735 ms，Markdown parse 约 3668 → 926 ms。新 bundle 的快照创建/事务函数与源码已核对；包含时间有重叠，不能相加。第一次章节解析、卡片正文准备和每次新保存的一次解析仍同步进行。

下一批 **PERF3G 画布首次准备与保存响应**：优先验证可取消的后台准备、精确源版本内的进一步复用及其生命周期，拆分解析/匹配/节点提交/落盘成本。保持全部候选、三文件、外部冲突和恢复核验，继续记录内存代价。当前模式切换 2249 ms 高于候选目标 300 ms，长帧 1154 ms 高于 100 ms；保存期间仍只读约 1.6–1.7 秒。PERF3 尚不能退出，UX6B / UX7 / UX8 / QA1 未开始；自动平排、真实 IME、物理多屏 DPI、干净安装/升级/卸载仍未验收，P0 未完成。
